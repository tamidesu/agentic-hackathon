# План работы — Halyk AI Challenge

Финальная версия. Составлен на основе проверенного инвентаря (`INVENTORY_files.md`).

## Исходные условия

| | |
|---|---|
| **Сейчас** | 5 дней с публичным датасетом. Есть `ground_truth.json` — можно измерять |
| **Потом** | 3 часа с приватным датасетом. Ключа нет, разработки нет, только прогон |
| **Сдаём** | один `submission.json` по структуре `submission_template.json` |

**Критерии оценки, в порядке приоритета:**

1. Количество очков — основной критерий
2. Время отправки — тайбрейк при равных очках
3. Качество решения и кода — архитектура, читаемость, обоснованность подхода

Из (2) следует: точность важнее скорости, но досиживать три часа ради ритуала не нужно — как только флаги разобраны и итерации перестали двигать результат, сабмитим.

Из (3) следует: модульность и README с обоснованием — это не гигиена, а баллы.

**Шкала одной ячейки:** `status` 0.50 (бинарно, ошибка обнуляет всю ячейку) · `actual` 0.30 × max(0, 1 − e/0.05) · `evidence_txn_id` 0.20 (при `null` в ключе убывает вместе с `actual`).

## Ключевое решение: обучения нет

Ни fine-tuning, ни обучения классификатора. 12 сценариев — это тест, а не обучающая выборка. Задача не «выучить закономерность по примерам», а «прочитать документ и посчитать по написанному в нём правилу», причём правило каждый раз новое и лежит в тексте договора.

**Разделение ответственности:**

- **LLM — экстрактор.** Читает документ, заполняет схему. Ни одного числа не выдаёт как ответ.
- **Код — решатель.** Берёт заполненные схемы и считает детерминированно.

Публичный датасет — инструмент валидации, а не тренировки. Ручная разметка окупается ровно в одном месте: ~50 транзакций как few-shot примеры для шага 10. Синтетика нужна не для обучения, а для проверки устойчивости — перемешанные копии публичного набора ловят хардкоды (шаг 16).

## Ключевое решение: RAG не нужен

Ретрив решает проблему «непонятно, какой документ читать». Здесь понятно детерминированно: `ACC-xxxx` в тексте → scenario_id через леджер, 190 документов из 200, ноль неоднозначностей. Из 200 файлов на один расчёт нужны 3–4.

Замерено: **~22k токенов на заёмщика** (документы + его строки леджера), **~264k на полный прогон**. Векторная база, чанкинг и реранкер здесь добавляют только шанс не подтянуть нужный кусок.

Отсюда же: стоимость не является фактором выбора модели. Ставим сильную модель везде; эмпирически проверяем более дешёвую только на шаге 10, где объём вызовов и задача узкая.

## Архитектура

```
200 PDF ──pdfplumber / tesseract──► artifacts/01_texts/   (49с + 16с на скан)
                                          │
                    regex-роутер: тип документа + scenario_id
                                          │
              ┌───────────────────────────┴────────────────────┐
              │   на каждого заёмщика, ветки независимы         │
              │   ┌────────────────────────────────────────┐   │
              │   │ LLM #1  договор  → covenant specs      │   │
              │   │ LLM #2  аудит    → корректировки       │   │
              │   │ LLM #3  KYC      → связанные стороны   │   │
              │   │ LLM #4  ~56 txn  → категории           │   │
              │   └────────────────────────────────────────┘   │
              │                      ↓                          │
              │   КОД: корректировки → агрегаты →              │
              │        status / actual / evidence              │
              └────────────────────────────────────────────────┘
                                     ↓
                             submission.json
```

**48 LLM-вызовов на прогон, 12 параллельных веток, ~5–10 минут.** Это и делает стратегию рабочей: в боевые 3 часа помещается 8–12 полных итераций.

### Контракты между шагами

Каждый шаг — отдельный скрипт: читает файлы-артефакты, пишет файлы-артефакты. Любой можно перезапустить или заменить целиком, не трогая соседние.

```
artifacts/
  01_texts/{doc_id}.txt          ← шаг 2
  02_doc_index.json              ← шаги 3, 4   {doc_id: {type, scenario_id, confidence}}
  03_covenants.json              ← шаг 5       {scenario: {point: spec}}
  04_adjustments.json            ← шаг 7       [{scenario, kind, target, value}]
  05_related_parties.json        ← шаг 8       {scenario: {parties[], threshold}}
  06_ledger_clean.csv            ← шаг 9
  07_ledger_categorized.csv      ← шаг 10      + category, confidence
  08_ledger_final.csv            ← шаг 11      + adjustment_log.json
  09_results.json                ← шаги 12,13  {scenario: {point: {status, actual, evidence, trace}}}
  submission.json                ← шаг 14
  flags.json                     ← шаг 15
```

Правило: **шаг не имеет права читать ничего, кроме своих объявленных входов.** Это то, что делает шаги независимо расширяемыми, и это же не даёт хардкодам расползтись.

## Блок 0. Основание

### Шаг 0 — Инфраструктура LLM-вызовов

**Вход:** ничего. **Выход:** `llm.py` + `cache/`

**Что сделать.** Обёртка вокруг вызова со structured output: JSON Schema на каждый тип извлечения (covenant spec, adjustment, related parties, transaction category). Кэш ответов по хэшу «промпт + схема + модель». Ретраи с бэкоффом. Батчинг транзакций. Лог всех вызовов с промптом и ответом.

**Research.** Не требует.

**Есть / чего не хватает.** Есть всё. Не хватает решения по модели — оно принимается не здесь, а по результатам первого полного прогона (шаг 12): ставим сильную по умолчанию, потом единственный осмысленный эксперимент — подмена модели на шаге 10 и замер дельты.

**Проверка.** Повторный прогон при полном кэше не делает ни одного сетевого вызова и даёт побитово тот же результат. Это критично: без кэша каждая итерация по шагу 12 заново гоняет извлечение, и цикл отладки растягивается с минут до часов.

**Риск.** Structured output гарантирует форму, а не смысл: модель вернёт валидный JSON с неверным порогом, схема пропустит. Валидация должна быть содержательной — порог положителен, направление ∈ {min, max}, период непустой.

**Точки расширения.** Новый тип извлечения = новая схема + новый промпт, регистрируются в реестре. Смена модели = один параметр. Добавление self-consistency = обёртка поверх, без правки вызывающих шагов.

### Шаг 1 — Скорер и валидатор

**Вход:** `submission.json`, `ground_truth.json` (только для скорера). **Выход:** `score.py`, `validate.py`

**Что сделать.** Два независимых инструмента.

*Скорер* воспроизводит официальную формулу с разбивкой по ячейкам. Работает только на публичном наборе.

*Валидатор* работает **без ключа** и проверяет формальную пригодность: ключи побитово совпадают с шаблоном, `status` ∈ {`COMPLIANT`, `BREACH`} заглавными, `actual` — число с двумя знаками, JSON парсится, пустых ячеек нет. **Именно он поедет в боевое окно.**

**Research.** Не требует. Формула задана в `CASE.ru.md`, раздел 4.

**Есть / чего не хватает.** Есть всё.

**Проверка.** Скорер: пустой submission → 0.00, submission из ground truth → 1.00, подмена одного `actual` на +2.5% → ровно половина его веса. Валидатор: подсунуть битый JSON, строковый `actual`, `status` в нижнем регистре, лишний ключ — каждый случай отлавливается.

**Риск.** `ground_truth.json` уже прочитан мной при сканировании, и это влияет на суждения. Он должен быть вынесен в `eval/`, недоступную коду пайплайна, а скорер — единственная точка контакта с ним. Отдельно: 36 ячеек — слишком мало, чтобы отличить улучшение от шума; разница 0.72 против 0.75 не значит ничего.

**Точки расширения.** Валидатор — место для любых новых инвариантов; каждый добавленный инвариант стоит дешево и работает вслепую.

## Блок 1. Детерминированный скелет

### Шаг 2 — Извлечение текста и OCR

**Вход:** `documents/`. **Выход:** `artifacts/01_texts/{doc_id}.txt` + отчёт о качестве

**Что сделать.** `pdfplumber` на всё; при длине текста ниже порога — `pdftoppm` + `tesseract -l rus+eng`. Результат кэшируется, весь пайплайн дальше работает по тексту.

**Research.** Не требует.

**Есть / чего не хватает.** Замерено: 200 файлов за **49 секунд**, OCR трёхстраничного скана — **16 секунд**. В публичном наборе ровно один скан (`f3fa6d20c8a1.pdf`, 3 стр.) — KYC Taraz Cement Works / ACC-7806 / P6.

Не хватает: качество OCR посредственное. Кириллица распознаётся с ошибками (`Cuër ACC-7806`, `Beneuynapuoe Bilajenve`), цифры и латиница (`ACC-7806`, `46.8%`, `38.1%`) — надёжно. Парсинг по русским ключевым словам на этом файле работать не будет.

**Проверка.** Ни один файл короче 500 символов, кроме OCR-ных. Для OCR-ных целевая проверка: находятся ли идентификатор счёта, все проценты долей и слово `KYC`.

**Риск.** Отбросить скан как нечитаемый — тогда P6 теряет единственный KYC и ковенант по связанным сторонам становится нерешаемым. Второй риск тоньше: OCR может исказить долю (38.1 → 38.7), а порог связанности 40% — ошибка распознавания напрямую переворачивает вердикт. Проценты со сканов проверяются глазами по изображению.

**Точки расширения.** Порог «мало текста» — параметр. Добавление второго OCR-движка или предобработки изображения — изолированная замена внутри шага. Если в приватном наборе сканов окажется много, здесь же настраивается параллелизм.

### Шаг 3 — Классификация типа документа

**Вход:** `artifacts/01_texts/`. **Выход:** `artifacts/02_doc_index.json` (поле `type`)

**Что сделать.** Детерминированный классификатор с **фиксированным приоритетом правил** — порядок важнее самих правил:

| # | Маркер | Тип |
|---|---|---|
| 1 | `НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ` | договор, устаревший |
| 2 | `Статья 6 — Финансовые ковенанты` | договор, действующий |
| 3 | `ДОПОЛНЕНИЕ О СОБЛЮДЕНИИ КОВЕНАНТОВ` | аудит финальный |
| 4 | `ПРОЕКТ — ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ` | аудит черновой — **не использовать** |
| 5 | `Знай своего клиента` / `KYC-ACC` | KYC |
| 6 | `Служебная записка казначейства` | казначейская записка |
| 7 | — | фон |

**Research.** Не требует.

**Есть / чего не хватает.** Проверено на 200 файлах, распределение: 12 / 12 / 12 / 5 / 12 (11 текстовых + 1 OCR) / 1 / 146.

**Проверка.** Счётчики совпадают ровно. Инвариант-ловушка: у каждого сценария **ровно один** действующий договор и **ровно один** финальный аудит — не ноль и не два.

**Риск.** Тематические слова текут между категориями: `Знай своего клиента` встречается **внутри текста договора** (пункт 6.3 ссылается на KYC), и при неверном порядке правил договор классифицируется как KYC — на этом сбоился мой первый проход. Второй, более опасный: `ИСПОЛНИТЕЛЬНЫЙ ЭКЗЕМПЛЯР` стоит на **обеих** редакциях договора и признаком актуальности не является ни при каких условиях.

**Точки расширения.** Правила — упорядоченный список пар (маркер, тип). Новый тип документа = одна строка в список. Если в приватном наборе появится незнакомый маркер устаревания, лечится здесь за минуту.

### Шаг 4 — Привязка документов к заёмщикам

**Вход:** `artifacts/01_texts/`, леджер. **Выход:** `artifacts/02_doc_index.json` (поле `scenario_id`)

**Что сделать.** Карта `account_id → scenario_id` **выводится из леджера в рантайме**: в каждой строке `txn_id` начинается со scenario_id, а `account_id` стоит рядом. Затем `ACC-xxxx` из текста документа → scenario_id. Fallback для документов без счёта — longest-match по названию компании. Сироты выносятся в отдельный список для ручного разбора.

**Research.** Не требует.

**Есть / чего не хватает.** Проверено: 190 из 200 документов содержат ровно один `ACC-7xxx`, мультипривязок ноль, коллизий подстрок между названиями компаний ноль. Карта публичного набора — `ACC-7201→B1, 7204→B4, 7801…7810→P1…P10` — **в код не попадает**, она выводится.

**Проверка.** Ноль неоднозначностей, каждый сценарий из шаблона получил хотя бы договор + аудит + KYC. Сироты выведены списком.

**Риск.** Считать всех сирот шумом — ошибка, я её уже допустил. `a5cc1400b640` — консолидированная отчётность **Sarybel Energy Holding JSC**, где прямо сказано, что Ekibastuz Power Services (P5) — её дочерняя структура; при этом в документе нет ни `ACC-7805`, ни имени заёмщика в шапке. Каждая сирота разбирается вручную, а не отбрасывается пакетно.

**Точки расширения.** Fallback-стратегии — упорядоченный список; можно добавить матч по БИН, по адресу, по имени аудитора.

### Шаг 9 — Подготовка леджера

*(Выполняется в день 1 вместе со скелетом; в нумерации оставлен на своём месте по смыслу.)*

**Вход:** `master_ledger_*.csv`, `submission_template.json`, `artifacts/04_adjustments.json` (для восстановления сумм — частично). **Выход:** `artifacts/06_ledger_clean.csv`

**Что сделать.** Отфильтровать строки, чей scenario_id **отсутствует в шаблоне** (не «начинается с 9» — это константа публичного набора). Восстановить пропущенные суммы из документов. Привести всё к USD.

**Research.** Не требует.

**Есть / чего не хватает.** Проверено: 1473 строки, дублей `txn_id` нет, все даты внутри периода, вне-периодных строк нет. 800 строк принадлежат счетам, **ни разу не упомянутым ни в одном документе** — подтверждённый шум; целевых 673.

Не хватает — и восстанавливается только из документов: **у двух транзакций пустое поле `amount`**.

| txn_id | сумма | источник |
|---|---|---|
| `TXN-P8-0031` | $884,204.16 (расход) | аудит P8, примечание 8.1 |
| `TXN-P7-0033` | $486,204.19 (расход) | **служебная записка казначейства** P7, раздел 4 |

15 транзакций целевых заёмщиков в EUR. Таблицы курсов в датасете нет намеренно: аудит раскрывает пофактовую сумму расчёта в USD (P3: `72,146.75 EUR → $83,690.23`), договор P3 прямо ссылается «по курсу, раскрытому аудитором».

**Проверка.** Ноль пустых `amount`, ноль строк не в USD, каждая конвертация имеет ссылку на конкретное примечание аудита. Количество целевых строк совпадает с суммой по сценариям шаблона.

**Риск.** Три способа тихо потерять данные. Первый — распарсить пустой `amount` как `0.0`: обе такие строки крупные (≈$0.5–0.9 млн) и обе влияют на результат. Второй — восстановить сумму из аудита (его читают все) и пропустить ту, что лежит в **единственной казначейской записке** — документе, который любой ретривер отранжирует низко. Третий — сконвертировать валюту по внешнему рыночному курсу вместо раскрытого аудитором: расхождение легко превысит 5% и обнулит и `actual`, и `evidence`.

**Точки расширения.** Механизм «пусто в леджере → искать в документах» пишется общим: сканировать все документы заёмщика на упоминание `txn_id` рядом с суммой. Два конкретных идентификатора в код не попадают. Сюда же вешаются новые виды дефектов данных, если приватный набор их принесёт.

## Блок 2. Извлечение фактов

### Шаг 5 — Парсинг ковенантов

**Вход:** `artifacts/02_doc_index.json` (действующие договоры). **Выход:** `artifacts/03_covenants.json`

**Что сделать.** Из каждого действующего договора извлечь Статью 6 и разобрать каждый пункт в структуру: тип теста, направление, порог, единица (сумма или коэффициент), период, определение показателя, оговорки. LLM со structured output.

**Research.** Не требует для извлечения.

**Есть / чего не хватает.** Есть все договоры, Статья 6 локализуется между заголовками. Не хватает — ничего, но объём недооценён: **определения различаются от заёмщика к заёмщику**. Проверено на публичном наборе:

| | 6.1 | 6.2 | 6.3 |
|---|---|---|---|
| B1 | покрытие процентов | Individual Overhead Line Ceiling | связанные стороны, сумма |
| B4 | выручка за Q4 | расходы по категории | связанные стороны, сумма |
| P1 | Capital Intensity Ratio | выручка по категории | связанные стороны, сумма |
| P2 | Cover of Applications by Sources | расходы по категории | связанные стороны, **доля** |
| P3 | **Springing** Drawdown Leverage | выручка по категории | связанные стороны, сумма |
| P4 | скорр. рентабельность | расходы по категории | связанные стороны, доля |
| P5 | капзатраты **Группы** | выручка по категории | связанные стороны, сумма |
| P6 | связанные стороны, доля | покрытие расходов на персонал | расходы по категории |
| P7 | налог./коммун. отношение | выручка по категории | связанные стороны, сумма |
| P8 | обязательства по персоналу | расходы по категории | связанные стороны, доля |
| P9 | доля активов у неогранич. лиц | выручка по категории | связанные стороны, сумма |
| P10 | страховое покрытие | выручка минус наибольшая статья | связанные стороны, доля |

**Риск.** Если прогон окажется не 5–10 минут, а час — вся стратегия с 8–12 итерациями рушится, останется одна попытка. Тогда приоритеты в боевом окне меняются полностью, и знать это надо на 5-й день, а не на приватном наборе.

# ФАЗА 2 — 3 часа на приватном датасете

**Правило поверх всего: валидный `submission.json` лежит на диске с 00:40 и обновляется только вверх.** Каждая версия сохраняется отдельным файлом. Худший исход — остаться без файла из-за поломки на 2:55.

| Время | Что |
|---|---|
| 00:00–00:10 | Распаковка. **Structure diff**: типы документов, наличие маркеров, колонки леджера, число сценариев, типы ковенантов, языки, доля сканов, дефекты данных |
| 00:10–00:25 | Триаж нового. Незнакомый тип теста → дописать функцию в реестр шага 6. **Это единственная разрешённая правка кода** |
| 00:25–00:40 | Первый полный прогон. **Сабмит сохраняется сразу** |
| 00:40–01:10 | Разбор флагов по убыванию цены |
| 01:10–01:25 | Прогон №2. Сабмит перезаписывается |
| 01:25–02:20 | Ручная проверка: сначала все `status`, потом `actual` коэффициентных тестов, потом `evidence` |
| 02:20–02:40 | Финальный прогон, валидатор формата |
| 02:40–03:00 | Резерв |

**Про тайбрейк по времени.** Он работает только при равных очках, поэтому досиживать до 3:00 бессмысленно: как только флаги разобраны и очередная итерация не двигает результат — сабмитим и освобождаемся. Но и сдавать в 01:00 ради минуты преимущества, оставив пять неразобранных флагов, — плохой размен: одна ячейка стоит дороже.

## Три места, где этот кейс проваливается

1. **Разные определения под одним номером пункта.** 6.1 у P1 — капиталоёмкость, у P6 — доля связанных сторон. Хардкод по номеру обнуляет ячейки целиком.
